# Phase 0 Research: Todo に課題と対応方針を残す

## Decision 1: 保存は Markdown、内部モデルは JSON 互換のオブジェクトにする
- **Decision**: 1件の Todo に対して 0 件以上の独立したコメント群を保持し、正本は通常の Markdown ファイルに保存する。読み込み後の `TodoEntry`、`TodoComment`、`DraftInput` は、TypeScript の型で表現した JSON 互換の内部オブジェクトとして扱うが、JSON ファイルを永続化しない。
- **Serialization**: コメント群は対象 Todo の直後に `<!-- quick-note-md:comments -->` と `<!-- quick-note-md:end-comments -->` で囲み、各コメントを `<!-- quick-note-md:comment -->` と `<!-- quick-note-md:end-comment -->` で囲む。各マーカーは必要なリストインデントを除き行頭に単独で置く。
- **Rationale**: 構造化された内部モデルならコメントの所属、順序、編集対象、未保存状態を扱いやすい。一方、Markdownを正本にすることで、憲章の「Markdown First」、拡張機能なしで読めるデータ所有権、既存Todoとの互換性を維持できる。JSONを別ファイルで永続化しないため、Markdownとの同期ずれや孤立コメントも避けられる。
- **Alternatives considered**:
  - TodoとコメントをJSONファイルへ保存: 構造化は容易だが、既存Markdownとの同期、拡張機能なしでの編集、外部変更の検出が複雑になる。
  - `todo-comments.md` や別Markdownファイル保存: 既存の単一Markdown管理と比べて追跡・同期が複雑化し、削除や移動時の整合性が落ちる。
  - タイトル末尾に注釈を埋め込む: 1 行で表現しきれず、Markdown 構造や長文が崩れる。

## Decision 2: コメント順序は作成順で固定し、手動並び替えは対象外とする
- **Decision**: コメント一覧の既定表示順は古いコメントから新しいコメントの順とし、MVP では手動並び替えを提供しない。
- **Rationale**: 003 の受入条件と FR-302 / FR-313 に一致し、編集時の状態遷移と競合解決を簡潔に保てる。
- **Alternatives considered**:
  - 任意順序 (ドラッグ＆ドロップ): UI 複雑化と保存差分が大きく、現在のデータモデルに対して不要な負荷が増える。
  - 逆順表示: 既存の「タスクの文脈を追う」用途に対して直感的でない。

## Decision 3: コメントは一つの Todo に属する独立した「ブロック」として扱う
- **Decision**: コメント本文は複数行 Markdown を許可し、各コメントは相互に依存せず独立した更新対象とする。返信スレッドやネストは導入しない。
- **Rationale**: 「背景」「調査」「対応方針」などを分離して残す目的を満たしつつ、更新範囲を限定できる。
- **Alternatives considered**:
  - 単一テキストの文字列として保存: 追記・修正の対象が曖昧になり、既存コメントの保持が難しくなる。
  - 返信ツリー構造: 本機能の範囲を超え、コメントの編集・削除と競合処理が複雑化する。

## Decision 4: Todo の識別と更新対象を行位置と文書コンテキストで固定する
- **Decision**: Todo は `file path + line position` を主要識別子とし、更新時には文書の現在行を再検証してから対象を確定する。コメント編集は選択した Todo のコメント群のみに限定し、タイトル・状態・他の Todo は変更しない。
- **Rationale**: 同名 Todo が複数存在するケースや、同一ファイル内の似た項目を誤って更新するリスクを抑えられる。FR-303/FR-307 に合致する。
- **Alternatives considered**:
  - 文字列一致のみ: 同名項目を混同する。
  - ファイル全体の再生成: 既存本文や他の Todo に影響しやすい。

## Decision 5: 既存コメント・新規コメントの両方を安全に追記・編集できるようにする
- **Decision**: 各コメントの本文は編集対象を明確にし、既存コメントを再編集する操作と、新しいコメントを末尾へ追加する操作を別経路で扱う。更新は対象コメントのみを書き換える。
- **Rationale**: 既存の記録を消さずに追記・訂正できるため、履歴の保持とユーザーの作業継続がしやすい。
- **Alternatives considered**:
  - コメント全体を丸ごと置換: 既存のほかのコメントや文脈を失う。
  - コメントごとの UUID 生成: Markdown 上での読みやすさが落ち、オフライン編集と相性が悪い。

## Decision 6: 状態とコメント編集の依存を切る
- **Decision**: Todo の状態（未完了／完了／Skip／Warn／IMP／Note）はコメント追加・編集の前提条件にしない。完了済みや Skip 状態の項目でもコメントを追加・編集できる。
- **Rationale**: FR-312 と 003 の要件に合致し、ユーザーが状態を戻さずに作業メモを残せる。
- **Alternatives considered**:
  - コメント追加前に自動再開: 状態が変わることで履歴やユーザー意図が壊れる。
  - 完了済みのみコメント不可: 要件で禁止される動作になる。

## Decision 7: 不明/破損時は読み取り専用で通知し、削除時は確認を必須とする
- **Decision**: コメント境界が曖昧な行や未知の記法があれば、対象 Todo を認識できない Todo として読み取り専用表示し、保存は行わない。Todo 削除時はコメント群も削除対象であることを確認し、キャンセル時は何も変更しない。
- **Rationale**: FR-304 / FR-307 の期待どおり、誤消失を防ぎながら安全に情報を保持する。
- **Alternatives considered**:
  - 破損箇所を自動破棄: 重要な情報の黙殺につながる。
  - 削除確認なし: 誤操作のリスクが高い。

## Decision 8: 競合・保存失敗・外部変更に対して安全に失敗させる
- **Decision**: 既存の「ファイル監視」「再検証」「保存失敗時は未保存文書を保持」方針を踏襲し、コメント更新で競合が起きた場合は古い内容を上書きせず、明示的に再読込・再試行を案内する。
- **Rationale**: 既存のデータ安全性と憲章 IV を満たし、未保存入力の消失や対象外ファイルの意図しない変更を防げる。
- **Alternatives considered**:
  - 自動再試行: 競合解消が不明瞭で、利用者の追跡が困難になる。
  - 失敗時に実行前状態を無視: 重要な内容が消える。

## Decision 9: 検証戦略を Markdown 解析と UI 行動に分離する
- **Decision**: コアの Markdown 解析・コメント抽出・順序保持・競合検出は単体テストで検証し、VS Code UI の追加/編集/削除フローは手動 + 主要 E2E シナリオで確認する。
- **Rationale**: 憲章の「コアロジックを API から分離してテストする」方針と整合し、今回の複雑な境界条件を再現しやすい。
- **Alternatives considered**:
  - 画面テストだけに依存: 解析ロジックのミスを見落としやすい。
  - 全機能を一度に自動テスト化: この機能の範囲に対して過剰で、初期実装のリスクが高い。
