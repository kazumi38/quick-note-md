# Feature Specification: メモのレンダリング切り替え表示・編集 & Todo 拡張ステータス

**Feature Branch**: `002-note-render-todo-status`

**Created**: 2026-09-20

**Status**: Draft

**Input**: User description: "追加要望で、ノートはレンダリングの切り替えやレンダリング中に編集できるようにしたい。また、TODOについては、単なるチェックだけでなく、Note や Skip、Warn、IMP など、つけたい。"

**Depends on**: [001-memo-todo-management](../001-memo-todo-management/spec.md)（メモ・Todo 管理の基本機能）

本仕様は、既存の「メモ & Todo 管理」機能を拡張するものであり、以下の2点を追加する。

1. メモ（Markdown ファイル）を、生テキスト編集表示とレンダリング（プレビュー）表示の間で切り替えられ、レンダリング表示中でもその場で内容を編集できること。
2. Todo 項目の状態を、完了/未完了の2値だけでなく、Note・Skip・Warn・IMP（重要）などの追加ステータスで分類できること。

## ユーザーゴール

- サイドバーやエディタから、メモを「読みやすい見た目（レンダリング表示）」と「編集しやすい生 Markdown」のどちらでも参照でき、切り替えの手間を最小限にしたい。
- レンダリング表示のまま、生テキストへの切り替え操作なしに内容を修正できること。
- Todo 項目に「完了/未完了」以外の状態（例: 参考メモとして残す Note、対応不要になった Skip、注意が必要な Warn、重要度が高い IMP）を付与し、サイドバーで区別して確認できること。
- これらの拡張状態も、依然として通常の Markdown ファイルとして保存され、拡張機能なしでもテキストとして意味が理解できること（憲章 I: Markdown First の継続）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - メモのレンダリング表示への切り替え (Priority: P1)

開発者が、サイドバーまたはエディタからメモを開いた際に、Markdown が整形された読みやすい見た目（レンダリング表示）で閲覧できるようにしたい。また、生の Markdown ソースを見たい・編集したいときは、いつでも切り替えられるようにしたい。

**Why this priority**: レンダリング表示は「メモを読む」という日常的な利用シーンの快適さに直結し、既存のメモ機能の価値を大きく高めるため最優先とする。

**Independent Test**: サイドバーからメモを開き、表示切り替え操作（コマンドまたはボタン）を実行するだけで、レンダリング表示 ⇔ 生 Markdown 表示が切り替わることを確認できる。

**Acceptance Scenarios**:

1. **Given** メモをレンダリング表示で開いている、**When** 「生 Markdown を表示」操作を実行する、**Then** 同じファイルの生 Markdown ソースが通常のテキストエディタで表示される。
2. **Given** メモを生 Markdown 表示で開いている、**When** 「レンダリング表示に切り替え」操作を実行する、**Then** 同じファイルがレンダリングされた見た目で表示される。
3. **Given** メモをサイドバーから初めて開く、**When** 項目を選択する、**Then** 既定の表示モード（レンダリング表示または生 Markdown、設定可能）でファイルが開かれる。
4. **Given** 表示モードを切り替えた、**When** 再度同じファイルを開く、**Then** 直前に使用していた表示モードが維持される、または既定モードが一貫して適用される（挙動は決定事項 D1 で確定）。

---

### User Story 2 - レンダリング表示中の直接編集 (Priority: P1)

開発者が、レンダリング表示のまま、生 Markdown 表示に切り替えることなくメモの内容を編集したい。

**Why this priority**: 「切り替えて編集し、また切り替えて読む」という往復操作をなくすことが、今回の追加要望の中核であり、日常的な軽微な追記・修正の速度に直結する。

**Independent Test**: レンダリング表示中のメモ本文をクリックして文字を入力・削除し、保存されることを確認できる。

**Acceptance Scenarios**:

1. **Given** メモをレンダリング表示で開いている、**When** 本文をクリックしてテキストを入力する、**Then** 入力内容が対応する Markdown ソースに反映され、ファイルに保存される。
2. **Given** レンダリング表示中に見出しや強調（太字・斜体など）を含む段落を編集する、**When** テキストを変更して保存する、**Then** 対応する Markdown 記法（`#`, `**`, `*` など）が破壊されずに維持される、または編集内容に応じて正しく更新される。
3. **Given** レンダリング表示中に Todo のチェックボックス行を編集する、**When** テキスト部分のみを変更する、**Then** チェック状態や拡張ステータス記号は変更されず、テキスト本文のみが更新される。
4. **Given** レンダリング表示中の編集で、拡張機能が解釈できない複雑な構造（テーブル、コードブロックなど）を扱う、**When** ユーザーがその部分を編集しようとする、**Then** 拡張機能は安全側に倒し、生 Markdown 表示へのフォールバックを促すか、当該部分の編集を許可しないことを明示する（データを破損させない）。

---

### User Story 3 - Todo に拡張ステータスを付与する (Priority: P1)

開発者が、Todo 項目に「完了/未完了」だけでなく、Note（参考情報として残す）、Skip（対応不要と判断した）、Warn（注意が必要）、IMP（重要）などのステータスを付けたい。

**Why this priority**: 単純な二値管理では表現できない実務上の分類ニーズに応えるものであり、Todo 機能の実用性を大きく高める。

**Independent Test**: サイドバーの Todo 項目に対してステータス変更操作を実行し、選択肢（Note/Skip/Warn/IMP/未完了/完了）から1つを選ぶと、対応する Markdown 行の記法が更新され、サイドバー表示にも反映されることを確認できる。

**Acceptance Scenarios**:

1. **Given** 未完了の Todo 項目を選択している、**When** 「ステータスを変更」操作を実行し「Warn」を選ぶ、**Then** 対応する Markdown 行が Warn を表す記法に書き換えられ、サイドバーで Warn として表示される。
2. **Given** Warn ステータスの Todo 項目がある、**When** 「ステータスを変更」操作で「完了」を選ぶ、**Then** 行は完了状態の記法に書き換えられる。
3. **Given** 複数の拡張ステータス（Note, Skip, Warn, IMP）を持つ Todo が混在する、**When** サイドバーの Todo ビューを見る、**Then** ステータスごとに視覚的に区別できる（アイコン・ラベル・グルーピングのいずれか、または組み合わせ）。
4. **Given** 標準の `- [ ]` / `- [x]` のみで書かれた既存の Todo 行、**When** 拡張機能がこれを読み込む、**Then** 「未完了」または「完了」ステータスとして正しく認識され、拡張ステータス機能導入前のデータと完全な後方互換性を保つ。

---

### User Story 4 - 拡張ステータスを含む Todo 一覧の閲覧 (Priority: P2)

開発者が、サイドバーの Todo ビューで、未完了・完了に加えて Note・Skip・Warn・IMP のステータスごとに項目を把握したい。

**Why this priority**: 分類機能自体（User Story 3）に比べ、一覧表示の見やすさは重要だが、まず分類・変更ができることが前提となるため優先度はやや下げる。

**Independent Test**: 複数ステータスの Todo が存在する状態でサイドバーを開き、ステータスごとの件数またはグループが表示されることを確認できる。

**Acceptance Scenarios**:

1. **Given** Note/Skip/Warn/IMP/未完了/完了の Todo が混在する、**When** サイドバーの Todo ビューを開く、**Then** 各ステータスの項目が識別可能な形（グループ分け、アイコン、ラベルなど）で表示される。
2. **Given** IMP（重要）ステータスの Todo がある、**When** サイドバーを見る、**Then** IMP 項目は他のステータスより目立つ形で（例: 一覧の先頭、強調アイコン）表示される。

---

### Edge Cases

- レンダリング表示中の編集によって、Markdown の構造（見出しレベル、リストのネスト、テーブル境界など）が意図せず破壊されそうになった場合、拡張機能は変更を保存せずユーザーに警告するか、生 Markdown 表示への切り替えを提案する。
- 拡張ステータス記法を使わない外部ツール（他の Markdown ビューアや Git の diff 表示など）でファイルを開いた場合、記号は読める文字として表示されるが、意味（Note/Skip/Warn/IMP）はツール側では解釈されない。この制約はユーザーに明示する。
- 同一行に対して、レンダリング表示中の編集操作とサイドバーからのステータス変更操作がほぼ同時に行われた場合、後勝ち（最後に確定した変更が反映される）とし、片方の変更が silently 消えないよう、少なくとも警告または再読み込みを行う。
- 拡張ステータス記法が壊れている、または未知の記号が使われている行は、「認識できない Todo」として扱い、既存の FR-025（001 仕様）と同様に変更せず表示のみ行う。
- レンダリング表示のみを提供し生 Markdown 表示を廃止する設計は行わない。ユーザーは常に生 Markdown 表示に戻れる（憲章 I: 拡張機能への非依存）。

## Requirements *(mandatory)*

### Functional Requirements — レンダリング表示・編集

- **FR-101**: システムは、メモ Markdown ファイルについて、レンダリング表示（整形されたプレビュー相当の見た目）と生 Markdown 表示の両方をサポートしなければならない。
- **FR-102**: システムは、ユーザーがこの2つの表示モードをワンアクションで切り替えられる操作（コマンドまたはボタン）を提供しなければならない。
- **FR-103**: システムは、レンダリング表示中に、ユーザーがテキストを直接編集できなければならない。編集内容は対応する Markdown ソースファイルに反映され、保存されなければならない。
- **FR-104**: レンダリング表示中の編集は、編集対象外の Markdown 記法（見出し記号、強調記号、リスト記号、チェックボックス記号、拡張ステータス記号など）を破壊してはならない。
- **FR-105**: システムは、レンダリング表示中の編集で対応できない複雑な構造（テーブル、コードブロック、埋め込み画像など）を検出した場合、データを破損させる可能性のある変更を行わず、安全側に倒す（編集を制限するか、生 Markdown 表示への切り替えを促す）。
- **FR-106**: システムは、メモを開く際の既定の表示モード（レンダリング表示 or 生 Markdown 表示）を提供し、ユーザーが設定で変更できるようにしなければならない。

### Functional Requirements — Todo 拡張ステータス

- **FR-107**: システムは、Todo 項目のステータスとして、少なくとも「未完了」「完了」に加え、「Note」「Skip」「Warn」「IMP」を提供しなければならない。
- **FR-108**: システムは、Todo 項目のステータスを、標準の Markdown タスクリスト記法（`- [ ]` / `- [x]`）を拡張した、プレーンテキストとして読める記法で表現しなければならない（憲章 I: Markdown First）。
- **FR-109**: システムは、ユーザーがサイドバーから Todo 項目のステータスを選択・変更できる操作を提供しなければならない。
- **FR-110**: ステータス変更操作は、対応する Markdown 行のステータス記号のみを書き換え、テキスト本文や他の行を変更してはならない。
- **FR-111**: システムは、001 仕様で定義された標準の `- [ ]` / `- [x]` のみで書かれた既存の Todo 行を、拡張ステータス導入後も「未完了」「完了」として引き続き正しく認識しなければならない（後方互換性）。
- **FR-112**: システムは、サイドバーの Todo ビューにおいて、各ステータス（未完了・完了・Note・Skip・Warn・IMP）を視覚的に区別して表示しなければならない。
- **FR-113**: システムは、拡張ステータス記号が壊れている、または未知の記号を含む行を「認識できない Todo」として扱い、内容を変更せずに扱わなければならない（001 仕様 FR-025 の延長）。

### Non-Functional Requirements

- **NFR-101（パフォーマンス）**: レンダリング表示への切り替え、およびレンダリング表示中の編集の反映は、一般的なサイズの Markdown ファイルに対して体感的に即時でなければならない。
- **NFR-102（信頼性）**: レンダリング表示中の編集、および Todo ステータス変更のいずれについても、ユーザーの既存データを黙って失わせたり、意図しない記法破壊を起こしたりしてはならない。
- **NFR-103（互換性）**: 拡張ステータス記法は、他の一般的な Markdown ビューア・エディタで開いた場合でも、プレーンテキストとして違和感なく読める形式でなければならない（意味の完全な解釈は拡張機能内に限られてよい）。
- **NFR-104（アクセシビリティ）**: 各 Todo ステータスの視覚的区別は、色だけに依存せず、テキストラベルまたはアイコン（代替テキスト付き）でも識別できなければならない。

### Key Entities *(include if feature involves data)*

- **表示モード (View Mode)**: メモを開く際の表示形式。値: レンダリング表示 / 生 Markdown 表示。ファイル単位、または拡張機能全体の既定値として保持される。
- **Todo ステータス (Todo Status)**: Todo 項目が取りうる状態の拡張列挙。値: 未完了 / 完了 / Note / Skip / Warn / IMP。001 仕様の「完了状態（true/false）」を拡張する概念であり、Markdown 上は特定の記号セットで表現される。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-101**: ユーザーは1操作でメモの表示モード（レンダリング表示 ⇔ 生 Markdown）を切り替えられる。
- **SC-102**: レンダリング表示中にテキストを編集し保存した場合、既存の Markdown 記法（見出し・強調・リスト・チェックボックス・拡張ステータス記号）が100%保持される。
- **SC-103**: ユーザーは2操作以内で Todo 項目のステータスを、未完了/完了/Note/Skip/Warn/IMP のいずれかに変更できる。
- **SC-104**: 拡張ステータス導入前に作成された既存の Todo Markdown ファイルが、拡張機能アップデート後も変更なく「未完了」「完了」として100%正しく認識される。
- **SC-105**: サイドバーを見た時点で、ユーザーは追加の操作なしにどの Todo が Note/Skip/Warn/IMP であるかを判別できる。

## Assumptions

- レンダリング表示は VS Code の Markdown プレビュー相当の見た目（見出し・強調・リスト・チェックボックスなどの整形）を指し、リッチテキストエディタや WYSIWYG エディタの完全な代替を意味しない（憲章 III: 単純さの優先、および Out of Scope の「リッチテキスト編集」との整合）。
- レンダリング表示中の編集は、まず「地の文（段落・見出し・リスト項目のテキスト部分）」の編集を主眼とし、テーブルや複雑なネスト構造など高度な直接編集は、初期バージョンでは生 Markdown 表示へのフォールバックで対応してよい。
- Todo 拡張ステータスの具体的な記法（Markdown 上でどの記号を使うか）は、既存の `- [ ]` / `- [x]` 記法との視覚的な一貫性を保ちつつ、プレーンテキストでも意味が推測しやすい記号を採用する（決定事項 D3 参照）。技術的な最終記法は技術計画（`/speckit-plan`）で確定する。
- Note ステータスは「対応済みだが記録として残したい」または「Todo ではなく参考メモ化したい」項目を表し、Skip は「対応しないと決めた」項目、Warn は「未解決だが注意喚起が必要」な項目、IMP は「優先度が高い未解決」項目、という意味で扱う（決定事項 D4 参照）。
- 既存（001 仕様）の「未完了」「完了」の二値モデルは廃止せず、拡張ステータスはこれに追加される選択肢として扱う。

## 重要な曖昧点の検討と決定事項

### D1. メモを開いたときの既定表示モードは何にすべきか？

- **重要性**: 既定モードはユーザーの第一印象と日常的な操作数に直結する。
- **選択肢**: (A) 常にレンダリング表示 (B) 常に生 Markdown 表示 (C) 直前に使用したモードを記憶 (D) 設定で選択可能。
- **決定**: (D) を採用し、既定値は (A) レンダリング表示とする。読む頻度の高いメモ利用シーンに合わせつつ、設定でユーザーの好みに調整できるようにする（憲章 II: VS Code 標準機構・ユーザー選好の尊重）。

### D2. レンダリング表示中に編集できない複雑な構造をどう扱うか？

- **重要性**: 無理に対応しようとすると Markdown 構造の破損リスク（憲章 IV: データ安全性）が高まる。
- **選択肢**: (A) 複雑な構造も含め全面的に直接編集を許可する (B) 複雑な構造は編集不可とし生 Markdown 表示への切り替えを促す。
- **決定**: (B) を採用する。安全性を優先し、テーブル・コードブロックなど構造的にリスクの高い要素は直接編集の対象外とする。

### D3. Todo 拡張ステータスをどのような Markdown 記法で表現すべきか？

- **重要性**: 記法の選択は、他ツールとの互換性、視認性、既存の `- [ ]`/`- [x]` との一貫性に影響する。
- **選択肢**: (A) チェックボックス内の記号を拡張する（例: `- [-]` Skip, `- [!]` Warn, `- [i]` IMP, `- [n]` Note のような一文字記号方式。Obsidian 等で採用例のある慣行に近い） (B) チェックボックスの後ろにタグ文字列を付与する（例: `- [ ] #warn テキスト`） (C) 完全に独自の絵文字・記号を行頭に追加する。
- **推奨**: (A) を推奨する。既存のチェックボックス記法との視覚的一貫性が最も高く、1文字追加のみで済むため Markdown としての可読性を損ないにくい。ただし正式な記号の割り当ては技術計画で確定する（Open Question 参照）。

### D4. Note / Skip / Warn / IMP の意味づけをどう定義するか？

- **重要性**: 意味が曖昧だとユーザーごとに解釈が割れ、一覧の分類価値が下がる。
- **決定**: Assumptions セクションで暫定的な意味づけ（Note=参考記録、Skip=対応しないと決定、Warn=注意喚起が必要な未解決、IMP=優先度が高い未解決）を採用する。この意味づけはヘルプドキュメントまたは設定の説明文でユーザーに明示する。

### D5. 拡張ステータス間の遷移に制約を設けるべきか？

- **重要性**: 任意のステータス間を自由に遷移できるべきか、一定の順序（例: 未完了→Warn→完了）を強制すべきかで UI 設計が変わる。
- **決定**: 制約は設けず、ユーザーはいつでも任意のステータス間を自由に変更できるようにする（憲章 III: 単純さの優先。状態機械の制約は不要な複雑性となるため導入しない）。

## Out of Scope（本仕様の対象外）

- レンダリング表示における画像・埋め込みコンテンツの高度な編集（リサイズ、キャプション編集など）
- テーブル・コードブロックなど複雑な構造のレンダリング表示中インライン編集（生 Markdown 表示へのフォールバックで対応）
- 拡張ステータスに対するユーザー独自のカスタムステータス追加機能（初期版は Note/Skip/Warn/IMP + 未完了/完了の固定セット）
- 拡張ステータスの自動遷移・通知・リマインダー機能
