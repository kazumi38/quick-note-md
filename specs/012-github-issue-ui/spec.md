# Feature Specification: GitHub Issue風UI

**Feature Branch**: `012-github-issue-ui`

**Created**: 2026-10-07

**Status**: Draft

**Input**: User description: "UIの変更をしたい。GitのissueみたいなUIにしたいから整理して"（添付画像を画面イメージとして参照）

## Clarifications

### Session 2026-10-07
- Q: GitHub Issue風の詳細・コメント・ラベル操作は、Todoだけに適用しますか、それともメモにも適用しますか？ → A: メモとTodoを共通のIssue風機能として扱う。
- Q: メモとTodoで詳細・コメント・ラベルを共通化したとき、Open／Close状態はどちらにも持たせますか？ → A: メモは状態なし、Todoは既存状態のままとし、詳細・コメント・ラベルのみ共通化する。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - サイドパネルでメモまたはTodoを作成する (Priority: P1)

ユーザーは、表示中の画面を離れたりポップアップに切り替えたりせず、横に開くサイドパネルからタイトルと複数行の説明を入力し、新しいメモまたはTodoを作成したい。どちらの種類も共通のIssue風詳細・コメント・ラベル機能で扱い、タイトルと本文の入力領域を分けて背景や対応方針を読みやすく記録できる。

**Why this priority**: 新規作成は情報を記録する最初の操作であり、分かりやすい入力画面がなければこの機能の価値を得られない。

**Independent Test**: 表示中の画面からサイドパネルを開き、タイトルと複数行本文を入力し、書式ツールを使った内容が入力中に整形表示されることを確認して保存する。作成後に一覧および詳細で内容を確認する。

**Acceptance Scenarios**:

1. **Given** ユーザーが項目を表示している、**When** 新規作成を開始する、**Then** 現在の画面を保ったまま横にサイドパネルが開き、タイトルと任意の複数行本文が別々の入力領域として示される。
2. **Given** タイトルと本文を入力している、**When** ユーザーが書式を設定する、**Then** 編集位置や選択範囲を失わず、書式結果が同じ入力面に即時反映される。
3. **Given** タイトルと本文が入力されている、**When** ユーザーが作成を確定する、**Then** 新しい項目が一件だけ作成され、入力内容が詳細画面で確認できる。
4. **Given** タイトルが空、または保存に失敗する、**When** ユーザーが作成を確定する、**Then** 無効な項目を作成せず、問題と修正または再試行方法を示し、入力中の本文を保持する。
5. **Given** ユーザーが作成を取り消す、**When** 破棄を選ぶ、**Then** 項目を作成せず、既存のメモやTodoも変更しない。

---

### User Story 2 - メモとTodoの詳細にコメント・ラベルを記録する (Priority: P2)

ユーザーは、メモとTodoのどちらについても、共通の詳細画面でタイトル、本文、コメント履歴、ラベルを確認し、新しいコメントの追加やラベルの編集を行いたい。Todoでは既存の状態操作も利用し、種類ごとの情報を一つのIssue風の表示で扱う。

**Why this priority**: 作成後も文脈を保ち、項目を継続して扱えるため。新規作成フォームを先に独立提供できるよう、作成画面より後の優先度とする。

**Independent Test**: 本文と複数のコメントを持つ項目を開き、表示内容・コメント順・状態操作を確認する。コメント入力中に書式結果が同じ編集面で反映され、コメント保存後も内容が保持されることを確認する。

**Acceptance Scenarios**:

1. **Given** 本文やコメント、ラベルを持つメモまたはTodoがある、**When** ユーザーが詳細を開く、**Then** タイトル、本文、コメント履歴、ラベルが識別可能な区分で表示され、Todoでは既存状態をラベルの横に表示し、メモには状態を表示しない。
2. **Given** コメント可能な項目が開かれている、**When** ユーザーが複数行のコメントを入力し、書式を設定して保存する、**Then** 入力中は同じ編集面で整形結果が即時反映され、保存後コメントが対象項目に一度だけ追加され、既存コメントや項目の他の内容は維持される。
3. **Given** 状態変更可能なTodoが開かれている、**When** ユーザーが既存の状態操作を選ぶ、**Then** Todoの既存状態と利用可能な次の操作が明示され、結果が画面に反映される。メモには状態変更操作を表示しない。
4. **Given** コメント保存または状態変更に失敗する、**When** 操作が完了しない、**Then** 変更が成功したかのように表示せず、入力中のコメントを失わずに失敗と再試行方法を示す。
5. **Given** 項目を表示している、**When** タイトル横の「…」から「タイトルを編集」を選ぶ、**Then** 現在のタイトルが入った編集欄が開き、保存しても本文・コメントは変わらない。
6. **Given** ラベルが0件または複数件ある、**When** ラベル用「…」から追加を選び、名前を入力して「追加」「適用」を選ぶ、**Then** 新しいラベルが状態の横に表示され、他の項目や状態は変わらない。
7. **Given** ラベルの編集欄を開いている、**When** 名前変更または取り外しを行い適用する、**Then** 対象項目のラベルだけが更新される。キャンセルすれば変更前の内容が保持される。
8. **Given** ラベルの編集欄を開いている、**When** 空白のみまたは同一表記の重複を追加する、**Then** 理由が示され、ラベル数は増えず、入力を修正して再試行できる。
9. **Given** 説明または既存コメントを表示している、**When** そのカード右上の「…」から編集を選ぶ、**Then** そのカード内に書式設定付きの編集欄が開き、項目全体の編集画面を開かずに修正できる。保存では対象本文だけが更新され、キャンセルでは元の内容が保持される。

### Edge Cases

- タイトルのみの項目、本文のみでは保存できない項目、本文やコメントが空の項目を一貫して扱い、空欄の表示を既定値と区別する。
- 長いタイトルや本文、複数行 Markdown、日本語、リンク、箇条書きを含んでも、入力・表示・既存コメントの境界が崩れない。
- 保存中に画面を閉じる、キャンセルする、または保存が失敗する場合に、未保存入力を黙って破棄しない。
- 書式の自動反映中に日本語変換、改行、貼り付け、Undo／Redo、段落をまたぐ選択・置換を行っても、入力やカーソル位置を失わない。
- 画面幅が狭い場合もサイドパネルの入力と確定・キャンセル操作が利用でき、背後の画面と取り違えない。
- コメントのない項目には空の履歴と追加操作を示し、コメントがある項目では作成順を維持する。
- 状態変更の操作が使えない項目や状態では、実行できない操作を成功可能なものとして表示しない。
- キーボード操作、画面読み上げ、色を識別できない状況でも、入力欄・状態・保存結果・操作を認識できる。
- Markdown 内の外部スクリプトやリモート画像を実行・自動取得せず、表示や編集によって対象外データを変更しない。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 新規作成 MUST ポップアップではなく、表示中の項目を維持したサイドパネルで提供し、パネル内にタイトルと任意の複数行本文を別々の入力領域として目的を明示して表示しなければならない。
- **FR-002**: ユーザー MUST タイトルを必須として新しいメモまたはTodoを作成でき、既存の項目種別ごとの作成規則が維持されなければならない。
- **FR-003**: 作成画面 MUST 作成の確定と取り消しを明確に区別し、取り消し時には項目を作成せず、既存データを変更してはならない。
- **FR-004**: 入力不備または保存失敗時 MUST 理由と次の操作をユーザーに示し、失敗を成功として表示せず、未保存のタイトル・本文を保持しなければならない。
- **FR-005**: 詳細画面 MUST メモとTodoのタイトル、本文、既存コメント履歴を区別して確認できるようにし、Todoに限り既存の状態を表示しなければならない。メモには状態を追加してはならない。
- **FR-006**: ユーザー MUST メモとTodoのどちらにも詳細画面からコメントを追加でき、追加後も既存コメントと対象項目のタイトル・本文を保持できなければならない。Todoの状態は変更してはならない。
- **FR-007**: 詳細画面 MUST Todoに限り既存の状態操作を提示し、ユーザーが選択した状態変更の結果を表示しなければならない。メモに状態操作を追加してはならず、コメントやラベル操作によってTodoの状態を暗黙に変更してはならない。
- **FR-008**: 保存または状態変更の失敗時 MUST 成功を示す表示を行わず、理由と再試行方法を示さなければならない。コメント入力中の内容は失敗によって失われてはならない。
- **FR-009**: 作成および詳細画面 MUST 既存の Markdown 内容を読み書き可能な形式とし、対象外の内容を変更または削除してはならない。
- **FR-010**: 新しい画面操作 MUST キーボードのみで実行可能であり、入力欄、状態、保存結果、操作の意味を色だけに依存せず識別できなければならない。
- **FR-011**: 画面文言 MUST 日本語を基本とし、既存のメモ、Todo、コメントのデータおよび操作との整合性を保たなければならない。
- **FR-012**: 本機能 MUST ローカルの既存メモ・Todo UIの表現を対象とし、GitHubとの同期、リポジトリ選択、担当者、通知、プロジェクト、メンション、共有ワークフローを追加または表示してはならない。
- **FR-013**: 本文編集 MUST ユーザーの入力に応じて見出し、強調、箇条書き、引用、コードなど対応する Markdown 書式の結果を同じ編集面に即時反映しなければならない。保存、改行、フォーカス移動、別のプレビュー操作を反映条件にしてはならず、日本語変換、カーソル、選択範囲、Undo／Redoを妨げてはならない。
- **FR-014**: 本文編集 MUST GitHub IssueのMarkdown書式操作を参考にした共通ツールバーを提供し、「見出し・太字・斜体・引用・コード・リンク」「箇条書き・番号付きリスト・チェックリスト」「元に戻す」の順にグループを区切って配置しなければならない。各操作は日本語の名前・ツールチップとキーボード操作で識別・利用可能にする。
- **FR-015**: コメント編集 MUST 本文と同等の即時書式反映と書式設定操作を提供し、日本語変換、カーソル、選択範囲、Undo／Redoを妨げてはならない。
- **FR-016**: 詳細画面 MUST メモとTodoのラベルを表示し、Todoではラベルを既存状態の横に表示しなければならない。メモでは状態を表示せず、ラベルを状態表示なしで確認できなければならない。
- **FR-017**: 詳細画面 MUST タイトルの編集をタイトル横の三点リーダー（…）メニューで提供し、本文やコメントと独立して変更・保存・キャンセルできなければならない。
- **FR-018**: メモとTodoのラベル領域 MUST 独立した三点リーダー（…）メニューを持ち、「ラベルを追加」「ラベルを編集」から名前の入力、対象項目内での名前変更、取り外しを行える編集欄を開かなければならない。ラベルが0件でも追加操作を利用できなければならない。
- **FR-019**: メモまたはTodoのラベル編集 MUST 「追加」で入力した名前を編集欄へ追加し、「適用」で変更を確定し、「キャンセル」で変更前のラベルを保持しなければならない。名前は前後の空白を除去し、空白のみと同一表記の重複を理由付きで拒否し、大文字・小文字は区別する。変更は対象項目だけに適用し、状態・本文・コメント・他の項目を変更してはならない。
- **FR-020**: 三点リーダーの操作 MUST 項目用とラベル用を名前で識別でき、キーボードで開閉・選択できなければならない。ラベル保存失敗時は入力を保持し、失敗理由を示さなければならない。
- **FR-021**: メモとTodoの詳細画面 MUST コメントの追加と既存コメントの編集を記入の中心として提供し、説明カードと各コメントカードの右上に個別の三点リーダー（…）メニューを置かなければならない。編集は対象カード内で行い、FR-013〜FR-015のリアルタイム整形・書式設定を適用する。保存は対象本文だけを変更し、キャンセルは元の内容・順序を保持する。保存失敗時は編集入力を保持して理由を示す。
- **FR-022**: 書式設定 MUST 選択した内容へ適用し、未選択時は入力位置に編集可能な書式のひな形を挿入する。見出しは1〜6段階、太字は`**本文**`、斜体は`_本文_`、引用は`> 本文`、単行コードはバッククォート、複数行コードはコードフェンス、リンクは`[表示名](URL)`、箇条書きは`- `、番号付きリストは`1. `、チェックリストは`- [ ] `としてMarkdownの意味を保持しなければならない。複数行のリスト・引用は各行に適用し、元に戻す／やり直すで書式操作と通常入力を取り消し・再適用できなければならない。
- **FR-023**: 書式ツールバー MUST 作成時の説明、新規コメント、説明の再編集、既存コメントの再編集で同じ機能と順序を提供しなければならない。GitHubのWrite／Preview切替を必須にせず、同じ入力面のリアルタイム整形を維持する。メンション、Issue参照、保存済み返信など書式以外のGitHub固有操作は本機能に含めない。

### Key Entities *(include if feature involves data)*

- **メモ／Todo**: 種類ごとの既存データを保ちつつ、共通のIssue風詳細画面で扱う個人用項目。タイトル、本文、ラベル、および0件以上のコメントを持つ。Todoのみ既存の状態を保持し、メモには状態を持たせない。
- **コメント**: 1件のメモまたはTodoに属する複数行の記録。詳細画面では対象項目と順序を保って表示する。
- **編集中の入力**: 保存前のタイトル、本文、またはコメント。保存結果や失敗時の再試行に関連するユーザー入力。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 代表的な新規作成テスト全件で、タイトルと複数行本文が入力後に正しい項目へ一度だけ保存され、再表示後の内容が一致する。作成操作はポップアップを使わず、表示中の画面を保ったサイドパネルで完了できる。
- **SC-002**: 入力不備、保存失敗、キャンセルの各テストで、誤った項目作成と既存データの意図しない変更が0件であり、入力内容が保持される。
- **SC-003**: メモとTodoそれぞれの詳細画面の確認テスト全件で、タイトル、本文、コメント履歴、ラベルが正しく区別され、Todoでは既存状態がラベル横に表示され、メモに状態は表示されず、コメント追加後も既存情報が維持される。
- **SC-004**: 対応する書式を入力した100回の検証のうち95回以上で、入力後500ミリ秒以内に、保存・改行・フォーカス移動なしで同じ編集面に書式結果が反映される。日本語変換中の入力欠落・重複と意図しないカーソル移動は0件である。
- **SC-005**: 代表的な作成、キャンセル、コメント追加、状態確認の操作を、マウスを使わずにすべて完了できる。
- **SC-006**: キーボードおよび画面読み上げによる利用確認で、すべての入力欄と操作の名前・目的・結果を認識でき、色のみで伝達される重要情報が0件である。
- **SC-007**: メモとTodoの双方におけるラベル0件・複数件・追加・名前変更・取り外し・キャンセル・空白のみ・重複・保存失敗の検証で、確定したラベルと再表示後の内容が一致し、対象外の変更と未保存入力の無警告消失が各0件である。
- **SC-008**: 説明、既存コメント、新規追加後のコメント、タイトルをそれぞれ編集・保存・キャンセルした全ケースで、対象以外の内容・状態・ラベル・コメント順序の変更が0件である。コメント編集は項目全体の編集画面への移動0回で完了できる。
- **SC-009**: 作成時の説明、新規コメント、説明の再編集、既存コメントの再編集の4種類すべてで、FR-014の10操作が同じ順序で利用できる。選択あり・なし、複数行、Undo／Redoの検証で、選択対象外の内容損失が0件であり、保存して再表示した書式の意味が一致する。

## Assumptions

- 添付画像はGitHub Issueの作成フォームと詳細・コメント操作の視覚的な参考であり、GitHubサービスとの連携要求ではない。
- 対象は既存のローカルメモ／Todo UIであり、保存形式、状態モデル、コメントの意味と保存方法は既存仕様を維持する。新しいデータ種別や共有機能は導入しない。
- 作成サイドパネルのタイトルと説明欄は既存の項目データに対応させる。担当者、リポジトリ選択、通知、プロジェクト、Issue番号など、アプリの既存モデルにない項目は追加も表示もしない。
- 詳細画面のコメント追加と状態変更は、既存のTodo機能が提供する場合に利用できる。状態管理機能を新規導入することは本仕様に含めない。
- 説明・コメントの自動書式表示は要望006の連続編集要件を引き継ぎ、入力と同時に同じ編集面で反映する。書式ツールバーはMarkdownの見出し、強調、リスト、引用、コード、リンクなど既存の内容形式で扱える機能を基本とする。
- 作成・キャンセル操作、失敗時の入力保持を標準の初期案とし、デスクトップ利用と既存の日本語UIを前提とする。狭い画面でもパネルの操作を利用可能にする。
- メモとTodoは共通のIssue風詳細・コメント・ラベル操作を利用する。種類ごとの既存状態モデルは維持し、メモに状態を追加しない。ラベルはTodoの状態と独立した任意の文字列とし、今回の名前変更は対象項目のラベルだけを変更する。全項目共通のラベル管理や一括改名は導入しない。
