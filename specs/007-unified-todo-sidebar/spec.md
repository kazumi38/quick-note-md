# Feature Specification: Todo 中心の統合メモサイドバー

**Feature Branch**: `007-unified-todo-sidebar`

**Created**: 2026-09-25

**Status**: Draft

**Input**: User description: "Note と Todo を統合し、Todo の折りたたみ一覧、本文とリプライのライブ Markdown 編集、色付きラベル、対応日を同じサイドバーで完結させる。"

**Depends on**: [001 メモ・Todo 管理](../001-memo-todo-management/spec.md)、[003 Todo 詳細](../003-todo-details/spec.md)、[004 Todo 優先度・ラベル](../004-todo-priority-labels/spec.md)、[005 サイドパネルメモ](../005-side-panel-notes/spec.md)、[006 ライブ編集](../006-live-note-editing/spec.md)

**Value**: 作業の背景、対応内容、会話の補足を Todo ごとに一か所へ集約し、中央エディタから離れずに確認・記録・完了できるようにする。

## Clarifications

### Session 2026-09-25

- Q: 新しい Todo の本文・リプライ・ラベル・対応日は、既存の Markdown 行にメタデータと境界マーカーを追加する形式で保存してよいですか？ → A: Todo 行を維持し、直後に Markdown 本文・リプライと明示的なコメント境界、属性メタデータを追加する。
- Q: ラベルの色は、ラベルごとにユーザーが選ぶ固定パレットから設定する方式でよいですか？ → A: ラベル名ごとに固定パレットから1色を設定し、全 Todo で共有する。
- Q: 本文・リプライ・属性の変更は、いつ Markdown ファイルへ保存しますか？ → A: ユーザーの明示的な保存操作で保存する。
- Q: 個別のリプライは、編集に加えて削除もできるようにしますか？ → A: 個別リプライを確認付きで削除できる。
- Q: 本文・リプライ・属性を持つ Todo を削除するとき、その Todo に属するすべての内容を確認付きでまとめて削除しますか？ → A: Todo と紐づく本文・リプライ・属性を確認付きでまとめて削除する。
- Q: 同じ名前のラベルを使う範囲は、すべての管理対象 Markdown ファイルを含むワークスペース全体で統一しますか？ → A: ワークスペース内の全管理対象 Markdown ファイルで同名ラベルの色を共有する。
- Q: 未保存の編集中に同じ Markdown ファイルが外部で変更された場合、保存時はどの方法で解決しますか？ → A: 自動統合せず、再読み込み・未保存内容のコピー・手動反映を選べる。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Todo の内容とリプライをサイドバーで記録する (Priority: P1)

ユーザーは、サイドバーの Todo 一覧から対象を展開し、タイトル、本文、リプライを同じ場所で読み書きしたい。本文には課題・方針・進捗を、リプライには時系列の補足を残し、完了済みの Todo でも必要に応じて更新したい。

**Why this priority**: Todo を単なるタイトルではなく作業の記録として扱うための中心的な利用フローである。

**Independent Test**: 既存のタイトルのみの Todo を展開し、本文と複数のリプライを追加・編集・保存した後、再読み込みして内容、順序、状態が保たれることを確認する。

**Acceptance Scenarios**:

1. **Given** タイトルのみの既存 Todo がある、**When** ユーザーがサイドバーでその Todo を展開して本文を記入・保存する、**Then** Todo のタイトルと状態を保ったまま、本文を後から再編集できる。
2. **Given** 本文を持つ Todo がある、**When** ユーザーが複数のリプライを追加・編集する、**Then** 本文とは別のリプライとして古いものから新しいものへ表示され、対象の Todo 以外は変更されない。
3. **Given** 完了、Skip、Warn を含む任意の状態の Todo がある、**When** ユーザーが本文またはリプライを編集する、**Then** 状態はユーザーが明示的に変更しない限り維持される。
4. **Given** 本文またはリプライにチェックボックスを含む Todo がある、**When** 一覧と未解決件数を表示する、**Then** それらのチェックボックスは独立した Todo として数えられない。
5. **Given** 複数のリプライを持つ Todo がある、**When** ユーザーが1件のリプライを削除して確認する、**Then** 選択したリプライだけが削除され、キャンセル時は本文とすべてのリプライが変わらない。
6. **Given** 本文、リプライ、ラベル、対応日を持つ Todo がある、**When** ユーザーが Todo の削除を要求して確認する、**Then** 対象 Todo とそれに紐づく内容だけがまとめて削除され、キャンセル時は何も変更されない。

---

### User Story 2 - 折りたたみ一覧から Todo を把握・整理する (Priority: P2)

ユーザーは、ファイル設定と Todo 一覧を同じサイドバーで使い、各 Todo の完了状態、タイトル、色付きラベル、対応日を展開せずに把握したい。必要な項目だけを展開して、詳細な本文とリプライを確認したい。

**Why this priority**: 作業中の画面を切り替えず、次に扱う Todo を素早く判断できるようにする。

**Independent Test**: 状態、複数ラベル、対応日の有無が異なる Todo を含む文書を開き、サイドバーだけで概要を確認し、任意の項目を展開・折りたたみして詳細を表示する。

**Acceptance Scenarios**:

1. **Given** 管理対象のファイルと複数の Todo がある、**When** ユーザーがサイドバーを開く、**Then** ファイル設定群と Todo 一覧を同じサイドバー内で利用できる。
2. **Given** ラベルまたは対応日を持つ Todo がある、**When** ユーザーが一覧を見る、**Then** チェック状態、タイトル、各ラベル、対応日を展開せずに確認でき、ラベルの意味と対応日の状態を色だけに依存せず判別できる。
3. **Given** 折りたたまれた Todo がある、**When** ユーザーが展開または折りたたむ、**Then** 対象 Todo の本文とリプライだけが表示または非表示になり、ほかの Todo の編集内容や展開状態を失わない。
4. **Given** 対応日が未設定、今日以前、未来の Todo がある、**When** ユーザーが一覧を見る、**Then** 未設定、期限切れ、期限内を区別できる。

---

### User Story 3 - Markdown を連続入力しながら内容を確認する (Priority: P3)

ユーザーは、Todo 本文とリプライを、改行や段落ごとに確定せず連続して入力したい。入力中に Markdown の整形結果を確認しつつ、必要な場合は生 Markdown の編集にも切り替えたい。

**Why this priority**: 長い作業記録を分断せず、書式を確認しながら記入できるようにする。

**Independent Test**: Todo 本文とリプライへ複数段落、見出し、箇条書き、リンクを連続入力し、保存前に整形結果を確認してから生 Markdown 表示へ切り替え、再表示後の意味が一致することを確認する。

**Acceptance Scenarios**:

1. **Given** Todo 本文またはリプライを編集している、**When** ユーザーが Enter、貼り付け、段落をまたぐ選択・置換を含めて入力する、**Then** 編集の確定操作を挟まず連続して入力できる。
2. **Given** 表示可能な Markdown を入力している、**When** ユーザーが入力を続ける、**Then** 保存、改行、フォーカス移動を待たずに同じ編集面で整形結果を確認できる。
3. **Given** 本文またはリプライに複雑または未知の Markdown 構造がある、**When** その構造を直接編集しようとする、**Then** 内容を変更せず、生 Markdown で編集する手段と理由を示す。
4. **Given** 未保存の本文またはリプライがある、**When** ユーザーが Todo・ファイル・表示方式を切り替える、**Then** 入力を保持するか、保存・破棄・キャンセルを選べ、黙って消失しない。

---

### User Story 4 - ラベルと対応日で Todo を分類する (Priority: P4)

ユーザーは、状態や優先度とは別に複数のラベルを設定し、任意の対応日を設定・変更・削除したい。色と文字の両方でラベルを識別し、対応日を設定しない Todo も通常どおり管理したい。

**Why this priority**: 内容を補完する属性によって一覧の見通しを改善するが、本文・リプライの記録を妨げない。

**Independent Test**: 1件の Todo に複数ラベルと対応日を設定し、ラベルだけを変更、対応日を設定・削除、完了状態を変更した後も、それぞれの属性が独立して保持されることを確認する。

**Acceptance Scenarios**:

1. **Given** Todo がある、**When** ユーザーが複数の名前付き・色付きラベルを追加または削除する、**Then** 空または重複したラベルは作成されず、状態、優先度、本文、リプライ、対応日は変わらない。
2. **Given** Todo がある、**When** ユーザーが対応日を設定、変更、または削除する、**Then** 対応日は任意属性として保存され、未設定に戻しても他の属性は変わらない。
3. **Given** 対応日を過ぎた未完了 Todo がある、**When** ユーザーが一覧を確認する、**Then** 期限切れであることを文字でも識別できる。完了済みの Todo は同じ日付を持っていても期限切れとして扱われない。

### Edge Cases

- 既存の通常メモ、タイトルのみの Todo、既存の詳細・コメント・ラベルを含む文書は、明示的な一括変換なしで読み取り、編集できる。対象外の本文、改行形式、同名の別 Todo は変更しない。
- 不明な記法、壊れた境界、所属を判定できない本文・リプライ・属性は破棄または自動修復せず、読み取り専用で表示して生 Markdown 編集へ案内する。
- 外部変更、競合、削除・移動、読み取り専用、保存失敗時は、古い内容を上書きまたは自動統合せず、失敗理由、外部変更版の再読み込み、未保存内容のコピー、手動反映、再試行の手段を示す。
- 個別リプライの削除時は、削除対象を確認してから反映する。キャンセル、競合、保存失敗時に本文や別のリプライを削除してはならない。
- Todo を削除するときは、削除対象の Todo、本文、リプライ、ラベル、対応日を明示して確認する。キャンセル、競合、保存失敗時に関連内容や他の Todo を削除してはならない。
- 日本語の変換中入力、長文貼り付け、狭いサイドバー、空の本文・リプライでも、キャレット、選択、未保存状態を失わない。
- 表示する Markdown に未完成の記法や外部コンテンツがあっても、外部スクリプトを実行せず、リモート画像を自動取得せず、安全に表示する。
- 日付に時刻を持たせず、利用者のローカル暦日で期限切れを判定する。日付として解釈できない既存値は変更せず、読み取り専用として扱う。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-701**: システムは、通常メモと Todo を共通の Markdown 文書として扱い、Todo に必須のタイトルと状態、任意の本文、0件以上のリプライ、0件以上のラベル、任意の対応日を関連付けなければならない。
- **FR-702**: システムは、既存の通常メモ、タイトルのみの Todo、既存の Todo 詳細・コメント・ラベルを明示的な一括変換なしで読み取り、従来の状態、内容、順序を保持しなければならない。
- **FR-703**: ユーザーは、同一サイドバーでファイル設定群と Todo 一覧を利用できなければならない。Todo 一覧の各項目は折りたたみ可能であり、一覧では状態、タイトル、ラベル、対応日を表示し、展開時は本文とリプライを表示しなければならない。
- **FR-704**: ユーザーは、Todo 本文を作成・閲覧・編集・保存できなければならない。本文の編集は Todo のタイトル、状態、ラベル、対応日、リプライ、他の Todo を明示的な操作なしに変更してはならない。
- **FR-705**: ユーザーは、Todo に属する独立したリプライを追加・閲覧・編集・保存・削除できなければならない。個別削除では対象リプライを明示して確認を求め、キャンセル時は何も変更してはならない。リプライは古いものから新しいものへ表示し、本文とは別のブロックとして保存・表示しなければならない。
- **FR-706**: 本文とリプライの内部にあるチェックボックスは Todo 一覧、状態集計、未解決件数に含めてはならない。
- **FR-707**: 本文とリプライは、改行、複数段落貼り付け、段落をまたぐ選択・置換を含め、行または段落ごとの編集開始・確定操作なしに連続して編集できなければならない。入力中の表示可能な Markdown は同じ編集面で整形結果を確認できなければならない。
- **FR-708**: ユーザーは、本文とリプライについて生 Markdown 編集へ切り替えられなければならない。直接編集の対象外または未知の構造は、黙って変更せず、生 Markdown 編集を案内しなければならない。
- **FR-709**: ユーザーは、状態や優先度と独立して、Todo ごとに複数のラベルを追加・削除できなければならない。各ラベルは名前と固定パレットから選ぶ1色を持ち、ワークスペース内の全管理対象 Markdown ファイルで同じ名前のラベルは同じ色を共有する。一覧で色と文字の両方により識別でき、空のラベルまたは同一表記の重複ラベルを作成してはならない。
- **FR-710**: ユーザーは、Todo ごとに任意の対応日を設定、変更、削除できなければならない。対応日は時刻を持たない暦日として扱い、未設定、期限切れ、期限内を一覧で文字により区別できなければならない。完了済み Todo は期限切れとして表示してはならない。
- **FR-710a**: ユーザーは Todo を削除できなければならない。削除前に対象 Todo と、紐づく本文、リプライ、ラベル、対応日が削除されることを明示して確認を求め、承認時は対象一式だけを削除し、キャンセル時は何も変更してはならない。
- **FR-711**: 本文、リプライ、ラベル、対応日の変更は、既存の文書管理経路を通じて対象 Todo の範囲だけを更新しなければならない。既存の Todo 行は維持し、その直後に人が読める Markdown の本文・リプライ、明示的なコメント境界、属性メタデータを置いて保存する。拡張機能なしでも内容と Todo との対応を読めなければならない。
- **FR-712**: 本文、リプライ、ラベル、対応日の変更は未保存として保持し、ユーザーの明示的な保存操作で Markdown ファイルへ反映しなければならない。競合または保存失敗時、システムは古い内容を黙って上書きまたは自動統合せず、保存済み・未保存・保存失敗を区別して表示し、外部変更版の再読み込み、未保存内容のコピー、手動反映、再試行を選べるようにしなければならない。
- **FR-713**: Todo、ファイル、表示方式、サイドバーの表示状態を切り替えるとき、システムは未保存の本文、リプライ、属性の入力を黙って破棄してはならない。
- **FR-714**: 未知または破損した Todo 構造は読み取り専用として保持し、対象外の内容、改行形式、同名の別 Todo、無関係なファイルを変更してはならない。
- **FR-715**: 新しい操作はキーボードだけで利用でき、状態、ラベル、対応日の状態、保存結果を色だけに依存せず識別できなければならない。日本語 UI と既存の Windows、macOS、Linux 対応を維持しなければならない。
- **FR-716**: 表示する Markdown 内の外部スクリプトを実行せず、リモート画像を自動取得してはならない。
- **FR-717**: 本機能で扱う Todo は個人用項目とし、担当者の割り当て、共有チャット、権限制御、通知、依存関係、手動並び替えを追加してはならない。

### Key Entities

- **統合 Markdown 文書**: 従来の通常メモと Todo を含む、ユーザーが拡張機能なしでも読んで編集できる文書。
- **Todo**: 統合 Markdown 文書に属する個人用作業項目。タイトル、状態、本文、ラベル、対応日、リプライを持つ。同名でも別項目として扱う。
- **本文**: Todo の課題、方針、進捗を記録する任意の複数行 Markdown。リプライとは独立する。
- **リプライ**: Todo に紐づく時系列の補足 Markdown。古いものから新しいものへ表示し、本文とは別に編集できる。
- **ラベル**: Todo の分類を示す、名前と固定パレットから選ぶワークスペース共有色を持つ複数設定可能な属性。同名のラベルは全管理対象 Markdown ファイルの Todo で同じ色を使い、状態と優先度から独立する。
- **対応日**: Todo の対応目安を示す任意の暦日。時刻を持たず、未設定・期限切れ・期限内の判定に用いる。
- **未保存入力**: 文書へ反映・保存されていない本文、リプライ、属性の変更。保存状態、競合、退避可能性をユーザーに示す対象。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-701**: タイトルのみの旧 Todo、本文、複数リプライ、複数ラベル、対応日、異なる状態、同名項目を含む20件の Todo で、編集・再読み込み・再起動後に、タイトル、状態、本文、リプライの内容と古い→新しい順、ラベル、対応日、所属が100%一致する。
- **SC-702**: 中央エディタの表示対象を変更する操作0回で、サイドバーから Todo の展開、本文の3段落入力、2件のリプライ追加、ラベルと対応日の設定、保存、再編集を完了できる。
- **SC-703**: 1,000行以内の統合 Markdown 文書において、本文またはリプライへの100回の表示可能な Markdown 入力の95%以上で、入力後500ミリ秒以内に同じ編集面で整形結果を確認できる。日本語の変換中入力は変換確定後から測定する。
- **SC-704**: 競合、保存失敗、外部での削除・移動、未知・破損した構造、Todo 本文・リプライ内のチェックボックス、未保存状態での切替を含む確認で、未保存入力の無警告消失、対象外内容の意図しない変更、Todo の二重計上、外部スクリプト実行、リモート画像自動取得が各0件である。
- **SC-705**: 状態、ラベル、対応日、保存状態の異なる20件以上の Todo で、一覧だけから各 Todo のタイトル・チェック状態・ラベル名・対応日状態を100%判別できる。色を無効にした確認でも同じ判別率を維持する。
- **SC-706**: 本文・リプライの編集、リプライ追加、ラベルと対応日の変更、展開・折りたたみ、保存、生 Markdown 切替の主要操作をキーボードのみで完了でき、既存の通常メモと Todo の閲覧・変更・保存の回帰確認がすべて成功する。

## Assumptions

- 要望中の「対応日」は任意の期限を示す日付とし、時刻・タイムゾーンを保存しない。期限切れの判定は利用者のローカル暦日を用い、完了済み項目は期限切れとして強調しない。
- Note と Todo は別ファイル種別へ移行せず、同じ Markdown 文書内で通常メモと Todo の文脈を保つ。既存 Todo 行を維持し、直後に人が読める Markdown の本文・リプライ、明示的なコメント境界、属性メタデータを置く。境界とメタデータの具体的な記号は、Markdown First と既存文書の後方互換性を満たすよう計画段階で決定する。
- 003 のコメントは本仕様のリプライへ統合して扱う。既存コメントの内容と古い→新しい順は保持し、本文・リプライの双方を編集できる。
- サイドバーの編集領域は、狭い幅でも本文とリプライの区別、保存状態、切替操作を確認できる可変領域とする。具体的な寸法と編集・プレビューの同時表示方式は計画段階で利用性を検証して決定する。
- Todo の既存状態と優先度は維持し、ラベル・対応日は独立属性とする。ラベルによる自動状態変更、対応日の自動完了、担当者・共有・通知・チャット送信は対象外とする。
- ラベルの色は、ラベル名ごとに固定パレットから1色を選び、ワークスペース内の全管理対象 Markdown ファイルで共有する。Todo ごとまたは Markdown ファイルごとに同名ラベルの色を変えず、色を使えない環境でもラベル名で識別できるようにする。
- 本文、リプライ、ラベル、対応日の変更は、入力中にライブ表示しても自動ではファイルへ書き込まない。ユーザーの明示的な保存操作でのみ反映する。
- 既存の管理対象、ファイル命名、文書保存・復旧の仕組みを継続利用する。共同編集のための排他制御や、既存文書の一括変換は追加しない。
