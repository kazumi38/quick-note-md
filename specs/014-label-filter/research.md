# Research: Issue 一覧のラベル絞り込み

## Decision 1: 既存一覧条件へ単一ラベル条件を追加する

- **Decision**: ラベルを0または1つ選択できる条件とし、検索語・Open／Closed 条件とANDで適用する。
- **Rationale**: 仕様は初期版の単一選択を前提としている。既存の `IssueSearchOptions` は検索語と状態を保持しており、一覧のソートや保存形式を変更せずに拡張できる。
- **Alternatives considered**: 複数選択は条件解釈（AND/OR）とUIの複雑さを加えるため対象外。検索語へのラベル名統合ではフィールド検索とラベル一致の意味が混ざるため採用しない。

## Decision 2: 候補は全有効 Issue から得て、表示条件は別に適用する

- **Decision**: 候補一覧は現在の検索語・状態・ラベルで絞る前の有効 Issue 全体から導出し、該当 Issue がない候補も選べる。破損 Issue は候補生成に使わない。
- **Rationale**: 仕様で候補を現在の検索結果に限定しないと定めており、候補が絞り込みによって消える循環を防げる。Issue の既存ラベル情報を再利用でき、独立したラベル台帳は不要。
- **Alternatives considered**: 現在の結果だけから候補を作ると、条件の変更後に使えるラベルが不安定になる。破損ファイルの原文走査は有効なラベルと確認できない値を混入させるため行わない。

## Decision 3: ラベルの既存同一性と読み取り専用の一覧操作を守る

- **Decision**: 保存済みラベルは前後空白を除去した値で比較し、大文字・小文字は区別する。フィルター変更では Issue データを更新しない。
- **Rationale**: `IssueStore.validateChanges` はラベル前後の空白除去と同一Issue内の完全一致重複拒否を行い、既存メタデータ契約は大小文字の異なるラベルを別値として扱う。検索操作から更新経路を呼び出す必要はない。
- **Alternatives considered**: 大文字小文字を同一視すると既存ラベル運用との互換性が崩れる。絞り込みのたびに Markdown を正規化保存する案は、閲覧操作による意図しない更新となるため採用しない。

## Decision 4: E2Eは既存のPlaywright VS Codeサイドバーシナリオへ追加する

- **Decision**: 既存 `e2e/issue-sidebar.spec.ts` とシードデータヘルパーを使い、P1からP3の利用者操作を独立して検証する。E2Eケースの具体的な手順・期待値は `quickstart.md` と UI contract に記録する。
- **Rationale**: プロジェクトにはVS Codeを起動するPlaywright E2E環境があり、検索・詳細から戻る既存テストもある。新しいテスト基盤を追加せず、ユーザーが実際に使うWebview経路を検証できる。
- **Alternatives considered**: Store/View単体テストだけでは、候補表示やWebview操作、条件保持を含むユーザー経路を確認できない。別のE2E基盤は不要な依存と保守負担を増やす。

## Unresolved questions

なし。初期対応の単一選択、候補範囲、比較ルール、永続化範囲は仕様と既存契約から確定できる。
