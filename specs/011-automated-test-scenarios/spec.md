# Feature Specification: テストシナリオ自動化

**Feature Branch**: `kazumi38-playwright-e2e-testing`

**Created**: 2026-10-07

**Status**: Draft

**Input**: User description: "playwrightでテストシナリオを自動テストを行いたい"

## Clarifications

### Session 2026-10-07

- Q: Playwrightによる自動テストの初期対象は、QuickNoteMDのどの操作範囲にしますか？ → A: チャットの主要操作のみ（新規作成・送信・既存会話への返信・保存失敗/競合）
- Q: 自動シナリオは、開発者の手元だけで実行できればよいですか、それとも変更のたびにCI（自動ビルド環境）でも実行しますか？ → A: 開発者のローカル実行のみ
- Q: Playwrightテストでは、VS Code上で動く実際のQuickNoteMDチャットを操作して確認しますか、それともチャットを模した独立したブラウザー画面を確認しますか？ → A: 実際のVS Code拡張機能とチャットを操作する
- Q: ローカルの自動テストは、Windows・macOS・Linuxのすべてで実行できることを初期要件にしますか？ → A: Windowsのみで実行する

## User Scenarios & Testing *(mandatory)*

### User Story 1 - チャットの主要操作を自動で確認する (Priority: P1)

開発者は、チャットを新規作成してメッセージを送る一連の操作を自動テストし、画面上の表示と保存された会話の両方が期待どおりであることを確かめたい。これにより、変更によってチャットの基本的な利用が壊れていないことを、手作業を繰り返さずに確認できる。

**Why this priority**: 新規チャットとメッセージ送信は、利用者が会話を始めるための中心的な操作であり、最初に信頼できる自動確認が必要である。

**Independent Test**: 空のテスト用ワークスペースから新規チャットを作成してメッセージを送信し、会話が表示され、保存先に期待した内容が残ることを確認する。

**Acceptance Scenarios**:

1. **Given** チャットがまだない空のテスト用ワークスペースで、**When** 開発者が新しいチャットを作成してメッセージを送信すると、**Then** チャットが一覧に現れ、送信した内容が会話に表示され、保存された内容にも反映される。
2. **Given** 自動テストが実行できる状態で、**When** 開発者が標準のテスト実行を行うと、**Then** このシナリオが人の操作なしで実行され、結果を確認できる。
3. **Given** 複数のシナリオがある状態で、**When** 開発者がこのシナリオだけを選んで実行すると、**Then** 他のシナリオの実行結果に依存せず完了する。
4. **Given** 実際の利用者のワークスペースが存在する状態で、**When** 開発者が自動テストを実行すると、**Then** テストは隔離されたデータだけを使用し、実際のワークスペースとノートを変更しない。
5. **Given** シナリオの期待結果を満たさない状態で、**When** 開発者が自動テストを実行すると、**Then** 結果から失敗したシナリオ、期待した結果、および実際の結果を特定できる。

---

### User Story 2 - 保存済みチャットを再開して返信する (Priority: P2)

開発者は、保存済みのチャットを開き、返信を送る一連の操作を自動で確かめたい。これにより、既存の会話を続けられることと、再開後の内容が正しく保持されることを確認できる。

**Why this priority**: 既存の会話を継続できることは、新規作成と同じくチャット利用の重要な流れである。

**Independent Test**: 事前に会話を用意したテスト用ワークスペースでチャットを開き、返信を送信して、画面と保存内容の両方を確認する。

**Acceptance Scenarios**:

1. **Given** 既存の会話が保存されたテスト用ワークスペースで、**When** 開発者がそのチャットを開いて返信を送信すると、**Then** 以前の会話と返信の両方が表示され、保存された会話にも返信が追加される。
2. **Given** 同じ初期データで自動テストを再実行すると、**When** チャットを再開して返信を送ると、**Then** 既存の会話が重複・欠落せず、同じ期待結果が得られる。

---

### User Story 3 - 保存できない状況で下書きを保護する (Priority: P3)

開発者は、保存先が読み取り専用または外部変更との競合状態にある場合に、送信した内容が失われないことを自動で確かめたい。これにより、データ保護の回帰を早期に発見できる。

**Why this priority**: データ保護は重要だが、正常な作成・返信の自動確認を先に提供した後に追加できる。

**Independent Test**: 保存に失敗する状態を再現したテスト用ワークスペースで送信を試し、失敗が明示され、入力内容が保持され、元の会話が壊されないことを確認する。

**Acceptance Scenarios**:

1. **Given** 返信の下書きを編集中に保存先が読み取り専用になったテスト用ワークスペースで、**When** 拡張機能が読み取り専用状態を検出すると、**Then** 送信操作が無効になり、その状態が一覧で分かり、入力内容が失われず、既存ファイルが変更されない。
2. **Given** テスト対象の会話がテスト実行中に外部から変更された状態で、**When** 開発者が変更後に送信を試すと、**Then** 競合が検出され、内容を黙って上書きせず、入力が保持される。
3. **Given** テスト用データの準備または後片付けが失敗する状態で、**When** 開発者が自動テストを実行すると、**Then** 失敗が明示され、該当シナリオを成功扱いにしない。

### Edge Cases

- 初期状態にチャットがない場合でも、新規チャットのシナリオを毎回同じ結果で実行できる。
- 空のメッセージを送ろうとした場合、空の会話を誤って保存しないことを確認できる。
- テストが途中で失敗または中断しても、テスト用データの後片付けが行われ、次回の実行結果に影響しない。
- テスト用データの準備に失敗した場合、テストを成功扱いにせず、失敗箇所を特定できる。
- 実際の利用者のワークスペースやノートを誤って変更しない。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 自動テストは、新規チャットの作成、メッセージ送信、一覧への表示、および保存内容の確認を一連の利用シナリオとして実行しなければならない。
- **FR-002**: 自動テストは、保存済みチャットの再表示と返信の送信・保存を確認しなければならない。
- **FR-003**: 自動テストは、保存不能状態（読み取り専用を検出して送信を無効にする場合を含む）と外部変更との競合を検出し、入力内容が保持され、既存データが黙って上書きされないことを確認しなければならない。
- **FR-004**: 各シナリオは、明示した初期状態と期待結果を持ち、単独でも実行できなければならない。
- **FR-005**: テスト実行ごとに隔離されたテスト用ワークスペースとデータを使用し、利用者の実際のノートやワークスペースを変更してはならない。
- **FR-006**: 同じ初期状態で繰り返し実行した場合、各シナリオは同じ判定結果となり、前回の実行データに依存してはならない。
- **FR-007**: 失敗時には、どのシナリオが失敗したか、期待した結果と実際の結果が何かを開発者が特定できなければならない。
- **FR-008**: テスト用データの準備または後片付けに失敗した場合、その問題を明示し、シナリオを成功扱いにしてはならない。
- **FR-009**: 初期リリースの自動テスト対象は、チャットの新規作成・送信、保存済み会話への返信、および保存失敗・競合時のデータ保護に限定し、メモや Todo など別機能は対象に含めない。
- **FR-010**: 自動シナリオはWindows上で開発者がローカル実行できなければならず、初期リリースでmacOS・Linux対応および継続的インテグレーション環境への組み込みは必須としない。
- **FR-011**: 自動シナリオは模擬画面ではなく、VS Code上で動作するQuickNoteMD拡張機能のチャットを操作し、画面表示と保存内容を確認しなければならない。

### Key Entities

- **テストシナリオ**: 初期状態、利用者の操作、期待結果、および実行結果を持つ自動確認の単位。
- **テスト用ワークスペース**: シナリオ専用のチャットデータを用意し、実際の利用者データから隔離する実行環境。
- **シナリオ結果**: シナリオの成否と、失敗時に期待結果・実際の結果を特定するための情報。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 新規チャット作成・送信と保存済みチャットの再開・返信について、定義された主要な受け入れシナリオの 100% が自動実行される。
- **SC-002**: 主要シナリオは、同一の初期データで連続 10 回実行したとき、毎回同じ判定結果になる。
- **SC-003**: 全シナリオの成否が自動で記録され、開発者がアプリ内で手動操作を行わずに結果を確認できる。
- **SC-004**: 保存失敗または競合のシナリオでは、入力の保持と既存データの非破壊を 100% 確認できる。
- **SC-005**: テストの失敗時、開発者は失敗したシナリオと期待結果・実際の結果を特定できる。

## Assumptions

- 初期対象は QuickNoteMD のチャット機能の主要な利用フロー（新規作成・送信、保存済み会話への返信、保存失敗・競合時のデータ保護）に限定し、メモ、Todo、および他機能は対象外とする。
- テストは開発者がWindows上でローカルに繰り返し実行できることを初期の利用方法とし、macOS・Linux対応および継続的インテグレーションへの組み込みは初期リリースの対象外とする。
- テスト対象は独立した模擬画面ではなく、VS Code上で動作するQuickNoteMD拡張機能とする。
- テストは専用の一時ワークスペースとデータを使い、実ユーザーのファイルにアクセス・変更しない。
- 既存のチャット保存形式と、競合・読み取り専用時のデータ保護挙動は維持する。
