# Feature Specification: メモ & Todo 管理（サイドバー統合）

**Feature Branch**: `001-memo-todo-management`

**Created**: 2026-09-20

**Status**: Draft

**Input**: User description: "VS Code の Primary Sidebar から、Markdown ファイルを唯一の永続データ形式として、メモの作成・閲覧・追記と、Markdown タスクリスト形式の Todo の作成・完了・再開・削除・参照を行える拡張機能を作る。ユーザーは拡張機能なしでも同じ Markdown ファイルを理解・編集できなければならない。"

## ユーザーゴール

- VS Code から離れずに、思いついたことをすぐメモとして書き留められること。
- 既存の Markdown メモに素早く追記できること（既存内容を失わないこと）。
- サイドバーから Todo を素早く作成・完了・再開・削除できること。
- メモも Todo も普通の `.md` ファイルとして保存され、拡張機能をアンインストールしても内容を理解・編集できること。
- サイドバーで、メモの一覧と、未完了/完了 Todo の件数・内容をひと目で把握できること。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - サイドバーからメモを素早く作成する (Priority: P1)

開発者が作業中に思いついたことを、VS Code を離れずにメモとして書き留めたい。サイドバーの「新規メモ」操作からタイトル（ファイル名の元）を入力するだけで、新しい Markdown ファイルが作成される。

**Why this priority**: メモ作成は本拡張機能の最も基本的な価値であり、これができなければ他の機能（追記・Todo）も成立しない。

**Independent Test**: サイドバーの「新規メモ」を実行し、タイトルを入力して確定するだけで、`.md` ファイルが作成され、サイドバーの一覧に表示されることを確認できる。

**Acceptance Scenarios**:

1. **Given** サイドバーの「メモ」ビューを開いている、**When** 「新規メモ」を実行しタイトルを入力する、**Then** ノートディレクトリ配下に新しい `.md` ファイルが作成され、一覧に表示される。
2. **Given** 新規メモ作成中、**When** タイトルを空のまま確定しようとする、**Then** 拡張機能はエラーメッセージを表示し、ファイルを作成しない。
3. **Given** 既に同名のファイルが存在する、**When** 同じタイトルで新規メモを作成しようとする、**Then** 拡張機能はファイル名の重複を検知し、連番を付与するか、ユーザーに別名を促す。

---

### User Story 2 - 既存メモへの追記 (Priority: P1)

開発者が既存のメモファイルに、既存内容を失うことなく新しい行を追記したい。

**Why this priority**: 追記はメモ運用で最も頻度が高い操作であり、既存内容の保護はデータ安全性の中核要件（憲章 IV）である。

**Independent Test**: 既存メモを選択して「追記」操作を実行し、テキストを入力するだけで、ファイル末尾に新しい行として追加され、既存内容が変化しないことを確認できる。

**Acceptance Scenarios**:

1. **Given** 末尾に改行のある既存メモ、**When** テキストを追記する、**Then** 既存内容はそのままで、末尾に新しい行としてテキストが追加される。
2. **Given** 末尾に改行のない既存メモ、**When** テキストを追記する、**Then** 拡張機能は追記前に改行を補い、既存の最終行と追記内容が連結されない。
3. **Given** 空のメモファイル、**When** テキストを追記する、**Then** 余分な先頭改行を挿入せずにテキストが1行目として書き込まれる。
4. **Given** 1つのメモに対して短時間に複数回連続で追記する、**When** それぞれの追記が完了する、**Then** すべての追記内容が実行順に、それぞれ独立した行として保持される（内容の欠落・上書き・順序の入れ替わりが発生しない）。

---

### User Story 3 - Todo の作成・完了・再開 (Priority: P1)

開発者がサイドバーから Todo 項目をすばやく作成し、完了したら一つの操作でチェック済みにし、必要なら再度未完了に戻したい。

**Why this priority**: Todo 管理はメモ管理と並ぶ本拡張機能の中核機能であり、日常的な操作の速さが製品価値に直結する。

**Independent Test**: サイドバーの「新規 Todo」からテキストを入力するだけで Todo が作成され、一覧の項目をクリック（または専用操作）するだけで完了/未完了が切り替わることを確認できる。

**Acceptance Scenarios**:

1. **Given** サイドバーの「Todo」ビューを開いている、**When** 「新規 Todo」を実行しテキストを入力する、**Then** `- [ ] <テキスト>` という形式の行が Todo 用 Markdown ファイルに追加され、「未完了」一覧に表示される。
2. **Given** 未完了の Todo が一覧にある、**When** 完了操作を実行する、**Then** 対応する行が `- [ ] ` から `- [x] ` に書き換えられ、「完了」一覧に移動する。
3. **Given** 完了済みの Todo が一覧にある、**When** 再開操作を実行する、**Then** 対応する行が `- [x] ` から `- [ ] ` に書き換えられ、「未完了」一覧に戻る。
4. **Given** Todo 一覧を表示している、**When** サイドバーを見る、**Then** 未完了件数が視覚的に（バッジまたは見出しのカウント）確認できる。

---

### User Story 4 - Todo の削除と参照元 Markdown を開く (Priority: P2)

開発者が不要になった Todo を削除したい、または Todo の元になっている Markdown ファイル・行を直接編集したい。

**Why this priority**: 削除と参照はコア操作（作成・完了）に比べ発生頻度は低いが、Todo 管理を完結させるために必要。

**Independent Test**: Todo 項目を選択して削除操作を実行すると当該行だけが削除され、他の行に影響しないこと、また「ソースを開く」操作でカーソルが該当行に移動することを確認できる。

**Acceptance Scenarios**:

1. **Given** 削除対象の Todo を選択している、**When** 削除操作を実行する、**Then** 確認ダイアログを経て、対象の1行だけが Markdown ファイルから削除され、他の行は変化しない。
2. **Given** Todo 一覧の項目を選択している、**When** 「ソースを開く」操作を実行する、**Then** 対応する Markdown ファイルがエディタで開かれ、カーソル（選択）が該当行に移動する。

---

### User Story 5 - 既存メモの一覧表示とエディタでの通常編集 (Priority: P2)

開発者がサイドバーからメモ一覧を見て、任意のメモを選び、通常の VS Code エディタで開いて自由に編集したい。

**Why this priority**: 「拡張機能に閉じ込められない」という中核価値（Markdown First 原則）を実現するために必須だが、作成・追記ほど頻度は高くない。

**Independent Test**: サイドバーのメモ一覧から項目を選択するとエディタでファイルが開き、そこで直接編集・保存した内容が次回のサイドバー表示や追記操作に正しく反映されることを確認できる。

**Acceptance Scenarios**:

1. **Given** ノートディレクトリに複数の `.md` ファイルが存在する、**When** サイドバーの「メモ」ビューを開く、**Then** すべての `.md` ファイルが一覧に表示される。
2. **Given** メモ一覧を表示している、**When** 項目を選択する、**Then** 通常の VS Code テキストエディタでそのファイルが開かれる。
3. **Given** エディタで直接メモを編集し保存した、**When** 再度そのメモに追記操作を行う、**Then** 直接編集された内容の末尾に正しく追記される。

---

### Edge Cases

- ノートディレクトリに、拡張機能が作成していない `.md` ファイル（外部で作成されたファイル）が存在する場合、メモ一覧に表示されるが Todo としては解釈されない（FR-024 参照）。
- 表示中に、参照していたファイルが外部から削除・移動された場合、サイドバーはエラーを出さずに一覧から項目を除去し、次の操作時にファイル不在を検知する（FR-020）。
- Todo ファイル内のチェックボックス記法が標準外（例: `-[ ]` のようにスペース欠落、`- [X]` の大文字、ネストしたリスト内のチェックボックス）である場合、可能な範囲で解析するが、解析できない行は「認識できない Todo」として扱い、一覧では非表示または別セクションに分類し、データを変更しない（FR-025）。
- 同一テキストの Todo が複数存在する場合、行番号やファイル内の位置で一意に識別し、操作対象を誤らない（FR-026）。
- 追記・完了・削除などの書き込み中に、対象ファイルが読み取り専用または他プロセスによりロックされている場合、書き込みを中止しエラーを通知する（FR-021）。
- 非常に大きな Markdown ファイル（数万行）に対する追記や Todo 走査でも、UI が固まらないこと。

## Requirements *(mandatory)*

### Functional Requirements — メモ

- **FR-001**: システムは、Primary Sidebar 上の専用ビューから新規メモ作成を開始できなければならない。
- **FR-002**: システムは、新規メモ作成時にユーザーからタイトル（ファイル名の元）の入力を受け付けなければならない。
- **FR-003**: システムは、入力されたタイトルから安全なファイル名を生成し、既定のノートディレクトリ配下に通常の `.md` ファイルとして作成しなければならない。
- **FR-004**: システムは、生成しようとしたファイル名が既存ファイルと衝突する場合、連番を付与するなどして自動的に一意な名前に解決しなければならない。
- **FR-005**: システムは、サイドバーに既存メモの一覧（ノートディレクトリ内の `.md` ファイル）を表示しなければならない。
- **FR-006**: システムは、一覧からメモを選択したとき、標準の VS Code テキストエディタでそのファイルを開かなければならない（独自のエディタ UI を要求してはならない）。
- **FR-007**: システムは、既存メモへの「追記」操作を提供し、ユーザーが入力したテキストをファイル末尾に新しい行として追加しなければならない。
- **FR-008**: 追記操作は、対象ファイルの既存内容を一切変更・削除してはならない。
- **FR-009**: 追記操作は、対象ファイルの末尾に改行がない場合、追記前に改行を補完し、既存の最終行の内容と追記内容が連結されないようにしなければならない。
- **FR-010**: 追記操作は、対象ファイルが空の場合、不要な先頭空行を挿入せずにテキストを書き込まなければならない。
- **FR-011**: システムは、同一ファイルに対して短時間に連続して行われる複数回の追記を、すべて欠落・重複・順序の入れ替わりなく処理しなければならない。
- **FR-012**: システムは、ユーザーが VS Code エディタで直接編集・保存したメモファイルの内容を、次回のサイドバー表示・追記・Todo 解析において正しい最新内容として扱わなければならない。

### Functional Requirements — Todo

- **FR-013**: システムは、Primary Sidebar 上の専用ビューから新規 Todo 作成を開始できなければならない。
- **FR-014**: システムは、新規 Todo 作成時にユーザーからテキストの入力を受け付け、既定の Todo 用 Markdown ファイルに `- [ ] <テキスト>` の形式で1行追加しなければならない。
- **FR-015**: システムは、標準 Markdown タスクリスト構文（`- [ ]` / `- [x]`）を Todo の完了状態の表現として使用しなければならない。
- **FR-016**: システムは、未完了の Todo を選択して完了状態に変更する操作を提供し、対応する行のチェックボックス記号のみを書き換えなければならない（テキスト本文は変更しない）。
- **FR-017**: システムは、完了済みの Todo を選択して未完了状態に戻す操作を提供しなければならない。
- **FR-018**: システムは、Todo を削除する操作を提供し、実行前に確認を求めなければならない。削除は対象の1行のみに影響し、他の行やファイル全体を変更してはならない。
- **FR-019**: システムは、サイドバー上で未完了 Todo と完了済み Todo を明確に区別して表示し、未完了 Todo の件数を表示しなければならない。
- **FR-020**: システムは、Todo 項目から、その項目が定義されている Markdown ファイルおよび該当行を直接開く操作（ソースを開く）を提供しなければならない。
- **FR-021**: システムは、Todo の対象ファイルが読み取り専用、削除済み、または移動済みであることを検知した場合、書き込みを行わずにユーザーに理解可能なエラーメッセージを表示しなければならない。

### Functional Requirements — データ・ファイル管理

- **FR-022**: システムは、メモと Todo を含むすべてのユーザーデータを、拡張機能なしでも開いて理解・編集できる標準 Markdown ファイルとして保存しなければならない。
- **FR-023**: システムは、既定のノートディレクトリ（ワークスペース内、既定値: `notes/`）配下の Markdown ファイルをメモとして検出・一覧表示しなければならない。ユーザーはこのディレクトリを設定で変更できる。
- **FR-024**: システムは、ノートディレクトリ内に拡張機能が作成していない既存の `.md` ファイルが見つかった場合も、通常のメモとして一覧に表示しなければならない（外部作成ファイルの排除や無視をしてはならない）。
- **FR-025**: システムは、標準的でない、または解析できないタスクリスト行に遭遇した場合、その行を変更せず、識別できない Todo として扱い、通常の Todo 一覧には含めない。
- **FR-026**: システムは、同一テキストを持つ複数の Todo 項目を、ファイルパスと行位置によって一意に識別し、操作（完了・削除など）の対象を取り違えてはならない。
- **FR-027**: システムは、Todo 用 Markdown ファイルが存在しない場合、初回の Todo 作成時に自動的に作成しなければならない。
- **FR-028**: システムは、拡張機能の外部（他のエディタ、OS のファイル操作など）で行われたファイルの作成・変更・削除・リネームを検知し、サイドバーの表示を実用上妥当な範囲で更新しなければならない。

### Functional Requirements — エラー処理

- **FR-029**: システムは、ファイル作成・書き込みに失敗した場合、原因を専門用語に頼らずユーザーに理解可能な形で通知し、操作を安全に中止しなければならない（部分的な書き込みや不整合な状態を残してはならない）。
- **FR-030**: システムは、サイドバーが参照していたファイルが外部で削除・移動されたことを検知した場合、エラーダイアログで操作を妨げることなく、一覧表示から静かに除去し、次回操作時に再検出を試みなければならない。

### Non-Functional Requirements

- **NFR-001（パフォーマンス）**: メモを開く、メモを作成する、追記する、Todo を作成する、Todo を完了させる、という操作は、一般的なサイズ（数百行〜数千行程度）の Markdown ファイルに対して、体感的に即時（概ね 300ms 未満での UI 応答開始）でなければならない。
- **NFR-002（信頼性）**: いかなる操作も、ユーザーの既存データを黙って失わせてはならない。書き込みに失敗した場合、元のファイル内容は変更前の状態のまま維持されなければならない。
- **NFR-003（互換性）**: 拡張機能は Windows、macOS、Linux で同等に動作しなければならない。ファイルパス、改行コード、権限モデルの違いに対して、いずれのプラットフォームでも安全に動作しなければならない。
- **NFR-004（アクセシビリティ）**: サイドバーの表示・操作は、VS Code 標準のキーボード操作、スクリーンリーダー対応、コントラスト要件に従わなければならない。状態（完了/未完了など）は色だけに依存せず、テキストまたはアイコンでも識別できなければならない。
- **NFR-005（保守性）**: サイドバー表示、Markdown 読み書き、メモ管理ロジック、Todo 解析・操作ロジック、設定管理は、それぞれ独立して理解・テストできるように分離されなければならない。

### Key Entities *(include if feature involves data)*

- **メモ (Memo)**: ノートディレクトリ内の1つの `.md` ファイルを表す。属性: ファイルパス、表示タイトル（ファイル名から導出）、最終更新日時。実装上の詳細（内部 ID など）は持たない。
- **Todo 項目 (Todo Item)**: Markdown ファイル内の1つのタスクリスト行を表す。属性: 所属ファイルパス、行位置、テキスト本文、完了状態（true/false）。同一ファイル内の行位置により一意に識別される。
- **Todo ファイル (Todo Source File)**: Todo 項目を1件以上含む Markdown ファイル。既定では1つの `todo.md` を既定の保存先とするが、他の Markdown ファイル内のタスクリスト行も Todo として認識してよい（FR-025, 決定事項参照）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: サイドバーからの操作だけで、ユーザーは3操作以内（例: ビューを開く → コマンド実行 → テキスト入力して確定）で新規メモを作成できる。
- **SC-002**: サイドバーからの操作だけで、ユーザーは2操作以内で既存メモへの追記を完了できる（対象メモの選択 → テキスト入力して確定）。
- **SC-003**: サイドバーからの操作だけで、ユーザーは1操作で未完了 Todo を完了済みに変更できる。
- **SC-004**: 追記操作を10回連続で実行したメモファイルにおいて、既存内容の欠落・重複・順序の入れ替わりが100%発生しない。
- **SC-005**: 一般的なサイズの Markdown ファイル（1,000行程度まで）に対する、メモを開く・追記する・Todo を完了するの各操作が、体感的に遅延なく完了する。
- **SC-006**: 拡張機能をアンインストールした後も、ユーザーは作成された `.md` ファイルをテキストエディタで開き、内容（メモ本文・Todo のチェック状態）を人間が読める形式で完全に理解できる。
- **SC-007**: サイドバーを開いた時点で、ユーザーは追加の操作なしに未完了 Todo の件数を把握できる。

## Assumptions

- ノートディレクトリの既定値はワークスペースルート直下の `notes/` とし、設定で変更可能とする（決定事項 D3 参照）。
- Todo は既定で単一の `notes/todo.md` に集約されるが、他の `.md` ファイル内の標準タスクリスト行（`- [ ]` / `- [x]`）も Todo として認識・表示・操作対象とする、いわゆる「ハイブリッド方式」を採用する（決定事項 D1, D2 参照）。
- メモと Todo の区別は、ファイル種別ではなく行単位で行う。すなわち、あるファイルがタスクリスト行を含んでいれば、それらの行は Todo としても表示され、同じファイルの他の部分は通常のメモ本文として扱われる（決定事項 D4 参照）。
- ファイル名は入力されたタイトルから安全な形式（英数字・ハイフン・日本語などを許容しつつ、OS で使用できない記号を除去）に変換して生成する。具体的な命名規則（日付プレフィックスの有無など）は技術計画（`/speckit-plan`）で確定する。
- 削除操作には確認ダイアログを必須とする（決定事項 D7 参照）。
- 外部ファイル変更の検知は VS Code のファイルシステム監視 API を利用する想定だが、具体的な実装は技術計画で決定する。
- ユーザーは基本的にシングルルートのワークスペースを使用する。マルチルートワークスペースでの複数ノートディレクトリの扱いは、初期バージョンではワークスペースの最初のフォルダを対象とする。
- 想定するメモ・Todo ファイルの規模は個人利用レベル（数百〜数千行、ファイル数十件程度）であり、大規模チームでの共同編集は想定しない。

## 重要な曖昧点の検討と決定事項

以下は、仕様確定にあたって特に影響が大きいと判断した論点である。各項目について、論点の重要性、選択肢、推奨案（憲章に基づく）を示し、明確に決定できるものは決定事項として記録した。

### D1. Todo はすべて単一の `todo.md` に保存すべきか？

- **重要性**: Todo の保存場所は、検出ロジック・UI 構造・複数ファイル対応の複雑さに直結する。
- **選択肢**: (A) 単一ファイル固定 (B) 複数ファイル自由（メモ内混在のみ） (C) 単一ファイルを既定としつつ、他ファイル内の Todo も認識するハイブリッド方式。
- **決定**: (C) を採用する。新規 Todo 作成の既定保存先は `notes/todo.md` とし、単純さ（憲章 III）を優先しつつ、既にメモ内に書かれたタスクリストも無視しない（憲章 I: ユーザーの既存データを尊重）。

### D2. Todo 項目は通常のメモファイル内に存在してよいか？

- **重要性**: メモと Todo を完全に分離すると、ユーザーが自然に書いた `- [ ] ...` がサイドバーに反映されず「ロックイン感」につながる。
- **選択肢**: (A) 専用 Todo ファイルのみ認識 (B) すべての `.md` ファイル内のタスクリスト行を認識。
- **決定**: (B) を採用する。ユーザーがどの Markdown ファイルにタスクリストを書いても、サイドバーの Todo ビューに反映される。これは憲章 I（Markdown First）と整合する。

### D3. 拡張機能は専用ノートディレクトリ配下のファイルのみを管理すべきか？

- **重要性**: 対象範囲が曖昧だと、ワークスペース全体をスキャンする重い処理や、意図しないファイルへの誤操作につながりかねない。
- **選択肢**: (A) ワークスペース全体を対象 (B) 設定可能な単一のノートディレクトリのみを対象。
- **決定**: (B) を採用する。既定は `notes/` とし、設定で変更可能とする。範囲を限定することで単純さ（憲章 III）とパフォーマンスを両立する。

### D4. メモと Todo ファイルをどう区別するか？

- **重要性**: ファイル種別で区別するか、行内容で区別するかにより UI とデータモデルが大きく変わる。
- **選択肢**: (A) ファイル名や拡張子で区別（例: `todo.md` は特別扱い） (B) 行単位でタスクリスト構文の有無により判定し、ファイル種別による区別を行わない。
- **決定**: (B) を採用する。「メモ」と「Todo」は排他的なファイル分類ではなく、同じ Markdown ファイルの異なる側面（本文行 / タスクリスト行）として扱う。これによりユーザーは1つのファイルにメモと Todo を自由に混在させられる。

### D5. ユーザーが Markdown を直接編集した場合、どう振る舞うべきか？

- **重要性**: 拡張機能が古いキャッシュ情報を表示し続けると、ユーザーが気づかずに二重管理・データ不整合を起こす恐れがある。
- **決定**: 拡張機能はファイルシステムの変更を監視し、対象ファイルが変更されたら、次にそのファイルに関連する情報（メモ一覧、Todo 一覧）を表示・操作する際に最新の内容を再読み込みする（FR-012, FR-028）。

### D6. 同一テキストの Todo が複数存在する場合、どう扱うか？

- **重要性**: テキストが同じでも異なる Todo であるため、操作対象を誤ると意図しない項目を完了・削除してしまう。
- **決定**: ファイルパスと行位置（行番号）の組み合わせで一意に識別する。テキストの一致だけでは同一項目とみなさない（FR-026）。

### D7. Todo の元ファイルが移動された場合、どう振る舞うべきか？

- **重要性**: 移動を検知できないと、存在しないパスへの書き込みでエラーが発生し、ユーザーが混乱する。
- **決定**: システムはファイル監視によりリネーム/移動イベントを検知し、可能であれば内部参照を新しいパスに更新する。検知できない場合（例: 拡張機能が非アクティブな間の移動）は、次回操作時にファイル不在を検知し、ユーザーに再スキャンを促すエラーメッセージを表示する（FR-021, FR-030）。

### D8. 一般的な操作に必要な最小サイドバー操作数は？

- **重要性**: 「素早さ」が製品の中核価値であるため、操作数の上限を明確にしておく必要がある。
- **決定**: メモ作成・追記・Todo 作成は各2〜3操作以内、Todo の完了/再開は1操作で完結することを目標とする（SC-001〜SC-003）。

### D9. メモ作成後、即座に Markdown エディタを開くべきか？

- **重要性**: 毎回エディタが開くと、複数メモを連続作成する際に煩雑になる可能性がある一方、開かないと作成直後に内容を書けない。
- **選択肢**: (A) 常に自動で開く (B) 常に開かない（一覧に追加するのみ） (C) 設定で選択可能にする。
- **決定**: (A) を既定とする。メモ作成の主目的はその場で内容を書き始めることであり、作成直後にエディタを開くことがユーザーの自然な期待に沿う。将来的に (C) への拡張は妨げない。

### D10. メモへの追記はどの UI で行うべきか（入力ボックス／エディタ／その他）？

- **重要性**: UI 選択は操作速度と入力しやすさに直結する。
- **選択肢**: (A) VS Code の入力ボックス（Quick Input） (B) 対象ファイルをエディタで開いてカーソルを末尾に移動 (C) 専用の Webview フォーム。
- **決定**: (A) を既定とする。1行程度の短いテキストであれば入力ボックスが最速であり、憲章 II（VS Code 標準機構優先）および III（単純さ）に合致する。複数行の追記が必要な場合の扱いは技術計画で検討する。

### D11. Todo 作成時に保存先 Markdown ファイルを選択できるべきか？

- **重要性**: 選択肢を増やすと柔軟性は上がるが、操作数が増え「素早さ」を損なう。
- **決定**: 既定の保存先（`notes/todo.md`）に自動的に追加し、ファイル選択は求めない。これにより Todo 作成は最小の操作数で完結する（D8, SC-003 と整合）。将来的なオプションとしての「保存先選択」は本仕様の対象外（Out of Scope）とする。

### D12. 完了済み Todo 項目はどのように表示すべきか？

- **重要性**: 完了項目を常に表示すると一覧が煩雑になり、非表示にすると達成感や見直しの機会を損なう。
- **決定**: サイドバーの Todo ビューは「未完了」セクションと「完了」セクションを分離して表示する（初期案の階層構造を踏襲）。完了セクションは折りたたみ可能とし、既定では折りたたんだ状態で表示件数のみを示す。

## Out of Scope（初期バージョンの対象外）

- クラウド同期、ユーザーアカウント、オンラインデータベース
- AI によるメモ自動生成・要約
- 複数ユーザーでの共同編集・リアルタイムコラボレーション
- カレンダー連携
- 高度なプロジェクト管理機能（担当者、期限、優先度などの拡張属性）
- リッチテキスト編集、独自 Markdown エディタ
- 独自データベース形式での保存
- 複雑なタグ付けシステム
- 複雑な全文検索（初期版は単純なファイル一覧・行一覧に限定）
- モバイルアプリケーション
- Todo 作成時の保存先ファイル選択機能（D11 決定によりスコープ外）

## Open Questions（ユーザー確認が必要な事項）

現時点で、上記の決定事項により大半の重要な曖昧点は解消されている。ただし、以下は技術計画（`/speckit-plan`）に進む前にユーザーの意向確認が望ましい：

- **OQ-1**: ノートディレクトリの既定値を `notes/` とすることに異論はないか、別の既定値（例: `.notes/` や設定必須化）を希望するか。
- **OQ-2**: メモ作成直後にエディタを自動的に開く（D9）挙動でよいか、それとも設定でオフにできる必要があるか。
- **OQ-3**: 完了済み Todo の保持期間や自動整理（例: 一定期間後にアーカイブ）が必要か、それとも無期限に残してよいか。
